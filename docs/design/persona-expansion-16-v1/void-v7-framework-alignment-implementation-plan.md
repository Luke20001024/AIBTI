# ArcBTI 16 人格结果页 × VOID V7 近似框架对齐实施规划

> 文档状态：实施前规划
>
> 本轮边界：只冻结统一框架、内容模型、逐人格任务、实施顺序与验收门槛，不修改任何正式结果页、人格文案、图片数据或交互组件
>
> 目标路由：`/result/{slug}/` 共 16 个结果页
>
> 高保真参考：`/preview/void-v2/` 当前 V7 版本
>
> 主验收视口：390 × 844 CSS px，1:1，无缩放

## 0. 结论先行

当前 16 人格结果页不能继续在现有 `ResultStoryPage + <details>` 上做局部修补

下一轮实施应将 VOID V7 视为唯一共享框架基准，重建一套真正的数据驱动结果页系统。16 页在 UI、内容密度、图文比例、章节顺序和讲述方式上与 VOID 保持近似，只在人物构图、强调色、动作词、图片裁切和文案语气上做受控适配

目标不是逐像素复制 VOID，也不是允许各人格自由设计。整体按约 85–90% 共享、10–15% 个性化执行，让用户明确感到 16 页来自同一产品、同一编辑体系，同时不会像只替换标题和颜色

16 页共同遵守以下叙事链路：

1. 一张完整人格海报完成第一印象
2. `先说人话` 在一个紧凑段落中解释用户为什么属于该人格
3. `代表建筑师` 用真人肖像、人物钩子和独立人物档案把人格连接到真实建筑史
4. `三次实锤` 用三座真实建筑证明这种空间判断如何成立
5. `同频建筑师` 把结果扩展成可继续探索的建筑谱系
6. `RESULT LOCKED` 用三句判断、保存、分享、重测和来源完成结果收束

主页面负责快速交付判断，人物故事、作品深读和同频建筑师资料统一进入手机全高 Sheet

现有的四格人格说明、三个本能长段、原生 `<details>`、同一建筑师的额外作品冒充“同频延伸”等结构全部退出正式结果页

## 1. 核心目标

### 1.1 产品目标

- 让 16 个结果都达到当前 VOID 的内容完成度，而不是只有首屏海报完成
- 用户离开首屏后，最多再滑半屏就得到一条可以复述的人格判断
- 用户在首屏结束后 1 个手机屏以内遇到代表建筑师
- 用户在首屏结束后 1.5 个手机屏以内遇到第一座真实建筑
- 主页面保持编辑型、杂志型阅读节奏，深度信息进入 Sheet，不把页面撑成长知识库
- 每个结果都同时满足传播性、建筑知识可信度和手机阅读效率

### 1.2 内容目标

每个人格必须回答六个问题：

1. 你为什么是这个人格
2. 这种偏好在空间中到底表现为什么动作
3. 哪位建筑师真正把它建出来了
4. 三座作品分别证明了什么
5. 还有哪两位建筑师值得继续看
6. 用户最终可以带走哪三句判断

### 1.3 交互目标

- 全站结果页只有一种内容展开方式：`button → modal Sheet`
- 主页面不再使用 `<details>`、`<summary>`、页内长展开或箭头教程
- Sheet 支持关闭按钮、遮罩关闭、Esc、浏览器返回、焦点锁定、焦点恢复和底层滚动锁定
- JavaScript 不可用时，主页面核心判断、建筑师姓名、三座作品和同频建筑师仍存在于静态 HTML；详情按钮禁用

### 1.4 视觉目标

- 首屏继续使用已经验收的 780 × 1564 扁平海报，不重新拆成 HTML + 多层图片
- 首屏之后高近似采用 VOID V7 的纸张、窄体标签、正文密度、真实图片比例和无圆角编辑感
- 各人格保留自己的强调色与墨色，但排版比例、组件逻辑、阅读节奏和页面密度与 VOID 基本一致
- 内容区不依靠大量横线、圆角卡片、装饰底图或多余 UI 说明制造层级

## 2. VOID V7 高近似共享框架

### 2.0 对齐程度

| 层面 | 对齐要求 | 可变范围 |
| --- | --- | --- |
| 章节顺序 | 与 VOID 相同 | 不允许调换或新增长章节 |
| 主页面密度 | 与 VOID 接近 | 总高、段长和模块间距允许约 ±10% |
| 标题体系 | 同一字号、字重和行距级别 | 根据中文长度允许一行或两行 |
| 建筑师卡 | 同一信息层级和 CTA 位置 | 单人、双人或团队肖像允许受控构图变体 |
| 三座作品 | 同一全宽图、动作标签、钩子和按钮结构 | 图片 object-position、动作词和卡片文案不同 |
| 同频建筑师 | 同一双列 4:3 结构 | 名称较长时允许字号和换行微调 |
| Sheet | 同一组件、状态机和内容顺序 | 人物 Sheet 可因单人或双人调整首图比例 |
| Ending | 同一判断、保存、分享、重测和来源结构 | 强调色、人格判断和社交提示不同 |
| 色彩 | 保持纸张与墨色体系 | 每个人格只替换一个主强调色及对应浅色 |

不得把“个性化”解释为重新设计章节、恢复卡片网格、改变主页面信息层级或大幅增减内容。任何人格变体都必须由姓名长度、双人身份、真实图片比例或建筑内容需要触发，不能因为设计者主观想换版式

### 2.1 页面结构

| 顺序 | 模块 | 主页面必须出现 | Sheet 中出现 |
| --- | --- | --- | --- |
| 00 | Hero | 完整人格海报 | 无 |
| 01 | 先说人话 | 标题、两句判断、风格翻译、反面提醒 | 无 |
| 02 | 代表建筑师 | 人物钩子、姓名、年份、真人肖像、短简介、人物 CTA | 经历、建筑方法、与人格的关系、来源 |
| 03 | 三次实锤 | 三张真实作品图、三组动作标签、作品名、强钩子、作品 CTA | 图库、故事、现场看什么、今日价值、关键事实、带走判断、来源 |
| 04 | 同频建筑师 | 两张真实代表作图、两位建筑师、方法、差异、人物 CTA | 人物与方法、同频关系、第一座推荐作品、关键词、来源 |
| 05 | RESULT LOCKED | 三句判断、风格谱系、保存、分享、社交提示、重测、来源 | 分享反馈可使用轻量提示，不另开内容 Sheet |

### 2.2 手机尺寸锁定值

| 项目 | 目标值 |
| --- | --- |
| 主验收视口 | 390 × 844 CSS px |
| 页面内容宽度 | 390px 视口内无横向溢出 |
| 页面总高 | 建议 3,800–4,500px，特殊人格最多不超过 4,800px |
| 建筑师模块起点 | 页面 Y ≤ 1,300px |
| 三次实锤起点 | 页面 Y ≤ 1,750px |
| Digest 标题 | 约 24–27px |
| 正文 | 15–16px |
| 正文行距 | 1.38–1.46，禁止为了“高级感”无意义拉大 |
| 人物缩略肖像 | 约 118 × 164px，真人身份明确 |
| 作品主图 | 390px 宽，约 230px 高，按项目设 object-position |
| 同频建筑师图 | 4:3 |
| Sheet | 手机 100dvh；桌面最大 620px 宽、860px 高 |

### 2.3 组件锁定规则

- 无圆角卡片
- 无横向轮播
- 无 Tabs
- 无 `<details>` / `<summary>`
- 无大段 UI 说明“点击查看”
- 无 AI 生成具体建筑作品替代真实项目图
- 人物位只允许身份可核验的真人肖像或明确的人物合照，不允许代表项目图兜底
- 同频建筑师外层必须显示其真实代表作品，不允许使用主建筑师的第四、第五件作品顶替
- 每个模块最多一个主要 CTA 体系，不同时出现箭头、加号和教程性提示

## 3. 统一内容数据模型

16 页不得分别写 16 套 JSX。实施时建立一套 `ResultV7Content` 合同，由每个人格只提供内容和资产

```ts
type ResultV7Content = {
  code: ResultCode
  digest: {
    label: string
    title: string
    body: readonly [string, string]
    styleBridge: string
    caveat: string
  }
  architect: {
    sectionLabel: string
    sectionTitle: readonly [string, string]
    architectId: string
    portrait: MediaSource
    summary: string
    detailTitle: string
    detailBody: string
    methodTitle: string
    methodBody: string
    relationTitle: string
    relationBody: string
    cta: string
  }
  works: {
    title: string
    lead: string
    items: readonly [ResultWorkV7, ResultWorkV7, ResultWorkV7]
  }
  lineage: {
    title: readonly [string, string]
    lead: string
    items: readonly [RelatedArchitectV7, RelatedArchitectV7]
  }
  ending: {
    judgment: readonly [string, string, string]
    socialPrompt: string
    primaryAction: string
    secondaryAction: string
  }
}
```

### 3.1 每件作品的强制字段

```ts
type ResultWorkV7 = {
  buildingId: string
  instinct: string
  action: string
  cardHook: string
  cta: string
  detailTitle: string
  story: readonly [string, string]
  observations: readonly [string, string, string]
  significance: string
  keyFact: string
  takeawayTitle: string
  takeaway: string
  gallery: readonly [MediaSource, MediaSource]
}
```

### 3.2 每位同频建筑师的强制字段

```ts
type RelatedArchitectV7 = {
  name: string
  originalName: string
  years: string
  method: string
  body: readonly [string, string]
  detailTitle: string
  detailBody: string
  relation: string
  featuredWork: string
  workNote: string
  keywords: readonly [string, string, string]
  image: MediaSource
  sources: readonly SourceItem[]
  cta: string
}
```

### 3.3 图片和来源合同

每一张真人肖像、作品主图、作品详情图和同频建筑师代表作必须记录：

- 本地文件路径
- 中文 alt
- 人物或项目身份
- 来源页面
- 图片原始页面
- 作者或机构署名
- 当前授权状态
- 商业发布前动作：可保留、需复核、需替换、需购买授权

所有来源统一进入 `/result/{slug}/sources/`，不把散落链接直接堆在正文结尾

## 7. 内容生产流程

### 7.1 每个人格的编辑顺序

1. 冻结一句人格命题
2. 写两句可以直接读懂的空间行为
3. 写一句建筑史翻译
4. 写一句反面提醒
5. 把代表建筑师经历翻译为两段空间方法
6. 为三座作品分别确定一个动作词
7. 每座作品写外层钩子和 Sheet 六段内容
8. 核验两位同频建筑师及代表作品
9. 写三句结果收束与一条社交提示
10. 统一删除句末句号并做反复句式审计

### 7.2 四批实施顺序

四批只用于内容研究、事实审查和批量验收，不代表四套 UI。四个家族继续使用同一套高近似 VOID 框架、同一密度和同一 Sheet，仅通过内容、真实图片和强调色表达差异

#### Batch A / 共享框架校准

`VOID、SIGN、GRID、MIX`

- VOID：作为高近似框架参考，只做通用组件兼容，不重写已经成立的内容节奏
- SIGN：验证双人建筑师、符号人格和相关建筑师链路
- GRID：验证最克制人格不会变成空页面
- MIX：验证高密度人格在同一框架中仍然清楚

通过条件：四页主页面节奏一致，但人格语气、动作词、色彩和真实图片明显不同

#### Batch B / 骨架与法则

`SPAN、MASS、TECH`，连同已完成 GRID

重点：结构与系统内容不能写成同义重复；分别突出受力、重量、设备与秩序

#### Batch C / 场所与气候 + 记忆与符号

`ROOT、EAVE、TIDE、RUIN、HAND、ORNA`，连同 VOID、SIGN

重点：避免把地域、材料、生态和记忆写成怀旧审美

#### Batch D / 流动与改写

`VEIL、FLOW、PLUS`，连同 MIX

重点：轻、流动、加建和混合必须各自对应真实空间动作，不靠曲面或透明等视觉词偷懒

### 7.3 文案硬规则

- 单句能说清时不拆成列表
- 主页面任何单段不超过 70 个汉字
- Sheet 正文单段建议 55–110 个汉字
- 一个结果页最多保留一处预先批准的“不是”句式，禁止“不是……而是……”成批出现
- 禁止“别抄”“抄这个判断”等命令式口号
- 禁止只有建筑专业人士才懂的术语堆叠
- 梗必须紧跟可验证的建筑方法
- 所有可见文案去掉句末句号
- 双人组合、事务所和大型项目必须说明共同作者，不能重新退回英雄建筑师叙事

## 9. 风险与陷阱

### P0 风险

1. **只换组件，不补内容**：页面会长得像 VOID，内部仍然只有旧版浅内容
2. **建筑图继续冒充人物图**：必须从渲染逻辑中删除代表作品兜底
3. **同频建筑师名实不符**：名字写 A，下面却展示主建筑师的额外作品
4. **16 份复制粘贴组件**：会造成后续视觉和交互快速漂移
5. **直接修改冻结 VOID**：失去唯一可信基准

### P1 风险

1. 为凑齐图库下载低分辨率、身份不明或授权不明图片
2. 双人组合只展示其中一人，重新制造作者缺席
3. 每个人格都套用同一种“最会……”句式，网感变成模板腔
4. 为填充信息密度恢复大量四格卡、横线和列表
5. Sheet 内容过长，变成第二条无限页面
6. 分享功能只复制 URL，却没有人格海报保存和清晰反馈

### P2 风险

1. 桌面端为了“铺满”而放大字号，破坏移动端参考比例
2. 相关建筑师图裁切过窄，重新出现竖条建筑图问题
3. 每个强调色直接大面积铺底，导致纸张体系失去统一
4. 页面加载 16 × 大量图库时没有 lazy loading 和尺寸约束

- 关闭后焦点回到触发按钮

## 12. Review 策略

### 12.1 三轮 Review

#### Review A / 内容理由

逐段回答：“为什么要讲这一段，它为用户下一步理解增加了什么”

无法回答的段落删除，不以“资料很重要”为理由保留

#### Review B / 网感与易读性

- 用户能否在 3 秒内理解标题
- 钩子能否被单独截图传播
- 幽默是否来自人物或建筑事实
- 是否出现模板式“最会……的人”堆叠
- 是否可以用一句话替代三条分点

#### Review C / 手机视觉

- 使用真实 390 × 844 截图，不在桌面宽度凭感觉判断
- 每个模块同时与 VOID 基线和同家族其他三页比较
- 任何“看起来怪”必须回到字号、行距、图片比例、信息顺序或内容长度中定位

### 12.2 四个代表页的角色

| 页面 | 用于验证 |
| --- | --- |
| VOID | 共享框架对齐、克制密度、Sheet 完整度 |
| SIGN | 双人作者、网感、符号内容和同频建筑师真实性 |
| GRID | 极简内容不变空、不靠大字号撑页面 |
| MIX | 高信息密度仍然易读，不回到列表和卡片堆积 |
